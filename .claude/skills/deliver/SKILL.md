# deliver：任务收尾与交付

替代 Codex 时期冗长的验收报告。目标是让用户一眼看懂结果，同时把证据保留在 Git 里，而不是堆进文档。

## 步骤

1. **自查 diff**：`git status --short` 加 `git diff --stat`，逐个确认文件都属于本任务。确认没有 Key、`.db`/`.sqlite`、`.env` 或日志；可以用 `docs/VALIDATION.md` 中的敏感信息扫描命令。
2. **跑 verify skill**：改动较小时只跑相关测试路径，合 main 前必须跑全量。
2b. **实操验收**：任务涉及界面、接线、调度或 Provider 时，按 CLAUDE.md"验收分三层"的第 2 层执行。在隔离 profile 中启动真实构建，用真实的点击和输入走完用户路径，截图存到 `docs/verification/<任务>-screens/`；发现的体验问题先修复再交付。真实模型实测（第 3 层）由总控在合并前和用户一起完成。
3. **提交**：用 Conventional Commit 风格写提交信息（`feat:`/`fix:`/`docs:`…），正文写清楚做了什么、为什么做，以及验证结果的关键数字。
4. **更新状态**：只在 `docs/STATUS.md` 顶部的"当前状态"里改一两行（任务、分支、提交、状态），不写长段证据。确实需要保留的详细证据，写进 `docs/verification/<日期>-<主题>.md`。
5. **合 main**：只有用户明确批准才执行 `git merge --ff-only`；不 force push，不改写历史。

## 给用户的报告（控制在一屏内）

- **做了什么**：1～3 句，说明用户能看到或能用上的变化。
- **怎么验证的**：分三张表列出：自动化测试、实操验收（附截图路径和每张截图说明）、真实模型实测。没做的项明确写"未验证"。
- **影响**：是否改了契约、数据库、迁移或 IPC，没改就写"无"。
- **遗留问题**：最多列 3 条，必须是真实存在的问题，不要为了凑数写进去。
- **提交 SHA**，以及下一步要用户做的决定（如果有）。

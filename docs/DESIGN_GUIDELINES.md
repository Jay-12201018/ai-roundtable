# AI 圆桌设计规范

## 1. 文档定位与交付边界

本规范为 AI 圆桌的后续界面实现提供设计依据。除明确标注的当前原型与源码现状外，所有设计条款均为未来实现和验收规范。R00 仅制定文档、治理与验证规则；本文件不表示界面已经实现，不构成视觉、交互或可访问性验收通过的证据。

当前 [App.tsx](../src/renderer/App.tsx) 与 [styles.css](../src/renderer/styles.css) 是用于验证 Mock 协作闭环的深色固定三栏原型。它采用最小宽度 1080px，尚未落实本规范的双主题、响应式布局、完整信息结构与可访问性要求，不能视为完成设计。R00 不修改上述业务源码与 CSS。产品范围见 [SPEC](../SPEC.md)，协作规则见 [AGENTS](../AGENTS.md)，功能现状与交付边界见 [README](../README.md) 和 [STATUS](STATUS.md)。

后续实现以功能决定布局，以体验决定交互。可以参考 Codex 与 Claude 的克制、清晰层级和阅读体验，但应独立设计，禁止直接复制其页面、组件排列、品牌元素或视觉资产。

## 2. 产品体验原则

- 用户是主持人，需要持续知道当前目标、谁在发言、下一步将发生什么，以及如何介入。
- 阅读与输入优先。Agent 群聊共用一个时间线，工作流和状态为阅读提供上下文，不把聊天拆成多个模型窗口。
- 多 Agent 通过姓名、角色、模型及回合信息区分。颜色只作辅助，不能承担唯一的身份或状态含义。
- 导航、聊天、上下文是三种职责，不等于三块必须常驻的栏位。宽窗可以并列，窄窗按当前任务折叠。
- 运行状态以 Main Process 为权威。界面操作反馈与运行结果分开显示，不在点击按钮时提前宣称暂停、停止或完成。
- 生成中的内容、被停止的部分文本、历史原文和消息版本都应可追踪。操作不得用清空时间线掩盖失败或中断。
- 常用操作应直达；配置、调试细节与低频操作按需展开，避免占据正文空间。
- 使用简体中文。Provider、模型名称和代码标识符保留准确原名；技术名称不替代面向用户的作用说明。

## 3. 信息结构与布局职责

| 信息领域 | 主要内容 | 默认入口与呈现方式 |
| --- | --- | --- |
| 房间与任务导航 | 房间列表、新建、当前目标、历史任务 | 导航区域；折叠后由房间按钮打开抽屉 |
| Agent 群聊 | 共享公共消息、角色、流式输出、消息版本与分支 | 中央时间线，是主阅读区域 |
| 主持人 | 输入、点名下一位、插话、持续指令、运行控制 | 输入区和任务工具栏；持续指令按需展开 |
| 工作流 | 模板、成员顺序、当前阶段、轮数、超时与预算限制 | 上下文面板或独立配置视图 |
| 模型设置 | Provider、模型、Endpoint、Key 状态、连接测试 | 独立设置视图；聊天中只显示必要的模型摘要 |
| 产物 | PRD、会议纪要、行动项、代码候选、来源消息 | 上下文面板中的产物入口；预览可扩展为主区域 |

导航负责切换对象；聊天负责理解协作过程；上下文负责检查和调整当前任务。信息只保留一个主要编辑入口，其他位置使用摘要与跳转，避免出现不同步的配置副本。

任务头部保留目标、Run 状态、当前 Agent 与回合摘要。主持人控制靠近状态和输入区，不要求用户打开右侧面板才能 Pause 或 Stop。事件序列等诊断信息放入可展开的运行详情，不作为普通用户的首要信息。

模型设置必须区分 Mock 与真实 Provider。Key 默认遮蔽，使用“已配置 / 未配置 / 本次会话有效”等文字；不将真实 Key 复制到时间线、调试展示或产物。自定义 Endpoint 的确认、连接测试及模型列表结果分别呈现，不能把获取模型列表成功标记为生成能力已验证。

工作流模板覆盖自由群聊、两模型对话、起草—审查—修订—复审—定稿与深度辩论。用阶段名称和顺序说明协作，默认串行生成；界面不能暗示多个 Agent 并行生成。模板选择展示参与角色、结束条件与预计回合，费用只有在数据足够时估算，并标注估算依据。

## 4. 窗口适配规则

断点依据可用内容宽度，应用缩放后仍需按实际可用空间折叠。不得依靠全页面横向滚动或固定最小宽度维持三栏。

| 可用宽度 | 布局策略 |
| --- | --- |
| ≥1280px | 可采用导航 + 聊天 + 上下文三职责并列；上下文可关闭，聊天随之扩展 |
| 1024–1279px | 优先折叠上下文，导航可保持可见；上下文由按钮打开抽屉或切换视图 |
| <1024px | 聊天优先；导航与上下文按需打开，避免同时遮挡输入区 |

宽窗参考导航 200–240px、上下文 280–320px；实际值由内容决定，不把这两个范围作为强制固定宽度。聊天正文建议最大阅读宽度 760px，居中布局，长代码块可在块内横向滚动。输入区与正文对齐；主区域缩窄时允许标题、工具栏换行，不压缩文字到不可读。

必须覆盖以下桌面窗口：

| 视口 | 后续实现的预期验证点 |
| --- | --- |
| 800×600 | 默认聊天单主区；抽屉可关闭；状态、输入和 Stop 可达；长内容可滚动 |
| 1024×768 | 辅助上下文折叠；导航不挤压正文；配置通过明确入口访问 |
| 1280×800 | 可启用三职责布局；标题与控制不截断；正文保持合理行长 |
| 1600×1000 | 三职责布局可用；正文不随窗口无限拉宽；关闭面板后仍保持阅读宽度 |

抽屉打开时明确其标题、关闭入口和焦点范围，关闭后把焦点还给触发按钮。产物预览和设置可临时占用主区域，但必须有清晰返回入口，并保存聊天阅读位置与未发送输入。

## 5. 双主题设计 Token

默认跟随系统主题，允许用户显式选择浅色或深色，并保存选择。“跟随系统”应持续响应系统变化。所有内容与交互状态都需覆盖双主题，包括菜单、抽屉、错误提示、代码块、选中项、输入和禁用态，不允许只切换外层背景。

以下为设计 Token，尚未在实际组件中测量对比度。实现时根据组合后的背景、透明度、边框和字号验证；不得把此表当作对比度已通过的报告。

| Token | 浅色 | 深色 | 语义与约束 |
| --- | --- | --- | --- |
| `color.canvas` | `#F7F7F5` | `#161B18` | 应用画布 |
| `color.panel` | `#FFFFFF` | `#1D2420` | 主面板、菜单与弹层背景 |
| `color.subtle` | `#F0F1EE` | `#252E28` | 次级区域、代码块、轻微悬停背景 |
| `color.text.primary` | `#202722` | `#E6EBE6` | 正文、标题、主要标签 |
| `color.text.secondary` | `#535E57` | `#BAC5BC` | 辅助说明、时间、占位提示；不能通过额外降透明度削弱可读性 |
| `color.border` | `#DCE1DB` | `#354139` | 装饰性分隔、非必要面板边缘；不用于唯一的控件边界 |
| `color.accent` | `#2F6B52` | `#9AC7AA` | 主要操作、可操作链接、焦点强调 |
| `color.error` | `#A93434` | `#F09A94` | 错误文字、错误图标与输入错误边界 |
| `color.control.border` | `#7A897F` | `#768A7C` | 必须被辨认的控件边界；与相邻背景验证 3:1 |
| `color.onAccent` | `#FFFFFF` | `#161B18` | 实色 accent 按钮上的文字与图标；深色主题不可继续使用白字 |
| `color.accent.hover` | `#255B45` | `#B0D5BC` | 主要按钮悬停背景，继续使用对应 onAccent |
| `color.selection` | `#E3EEE6` | `#304237` | 房间选中与消息定位背景，叠加文本或形状标记 |
| `color.success` | `#2D6A43` | `#A2D5B0` | 成功反馈，始终带“已完成 / 已保存”等文字 |
| `color.warning` | `#7B5C17` | `#DFC284` | 预算、超时、中断等需关注的提示 |
| `color.info` | `#356489` | `#9CC3E0` | 中性信息提示，不用于 Agent 身份编码 |
| `color.focus` | `#2F6B52` | `#9AC7AA` | 键盘焦点轮廓；不得被裁剪或仅靠背景变化表现 |
| `color.scrim` | `rgba(22,27,24,0.28)` | `rgba(0,0,0,0.48)` | 模态遮罩；遮罩后内容不可作为交互目标 |

`color.border` 只用于不影响辨认的分隔线。按钮、输入与可交互图标如果依赖边界辨认，使用 `color.control.border` 或满足要求的实色背景；不得将低对比装饰线误作控件边界。错误提示使用 error 前景与 panel/subtle 背景，不默认将 error 作为实色按钮背景。

链接在正文中使用下划线或其他非颜色线索。Agent 姓名、模型名和正文统一遵循文字 Token，不按不同厂商涂成不同颜色。禁用态同时使用 `disabled` 语义和明确的禁用原因，不通过给整个容器降低透明度影响可读正文。

## 6. 字体、尺度与节奏

中文界面使用系统字体，不额外依赖远程字体。推荐字体栈为 `-apple-system, BlinkMacSystemFont, "Segoe UI", "PingFang SC", "Hiragino Sans GB", "Microsoft YaHei", "Noto Sans CJK SC", system-ui, sans-serif`。代码使用 `ui-monospace, SFMono-Regular, Menlo, Consolas, monospace`。

| 用途 | 字号 / 行高 | 使用规则 |
| --- | --- | --- |
| UI 标签、按钮、辅助说明 | 14px / 20px | 默认界面文本，不用小字隐藏状态与关键限制 |
| 消息正文 | 15px / 24px | 阅读优先，段落间距清晰，中文断行自然 |
| 代码 | 13px / 20px | 保留缩进；复制入口可键盘访问 |
| 区域标题 | 16px / 24px | 中等字重，与正文形成明确层级 |
| 任务标题 | 20px / 28px | 长标题允许换行，不能遮挡控制按钮 |

间距刻度固定为 `4 / 8 / 12 / 16 / 24 / 32px`。控件内部通常 8–12px，相关项目之间 8–12px，消息与区域间隔 16–24px，较大区域使用 32px。避免为每个组件增加独立的间距数值。

控件圆角 8px，弹层圆角 12px；正文消息不依赖大圆角卡片区分角色。常规按钮高度 36px，主要输入动作可用 40px；图标点击目标最小 32×32px，即使图形本身更小也应有完整可点击区域。高度可随文字缩放扩展，不能以固定高度裁切标签。

只在弹层需要表达层级时使用轻阴影。禁止花哨渐变、按 Agent 分色的彩色卡片、装饰性光晕、持续跳动或与任务无关的动画。

## 7. 时间线、输入与阅读交互

每条消息采用统一结构：发送者姓名与角色 → 可选模型、回合和时间摘要 → 正文 → 消息状态与操作。主持人、Agent 和系统消息可通过角色标签、头像首字或图标区别，均有可读文字身份。系统消息使用紧凑说明行，不模拟某个 Agent 发言。

流式正文持续追加到同一条消息。状态文字使用“生成中”；完成、失败或停止后更新状态，但保留已有文本。消息操作如复制、修改、重新生成、查看版本由明确按钮或菜单提供，不能只在鼠标悬停时出现且键盘无法到达。

Markdown 安全渲染，不执行模型返回的 HTML 或脚本。代码块保持语言、缩进与可复制性，超长代码只在代码块内滚动；错误和空代码块不能撑破窗口。公开推理摘要只在 Provider 真正提供时展示，并明确标注来源，不伪造完整思考过程。

阅读滚动规则：用户在底部阅读时可跟随新增消息；用户向上翻阅、选中文本或查看旧版本时停止自动抢滚动，提供“有新消息 / 回到最新”入口。虚拟列表应保留稳定消息标识、滚动锚点和键盘阅读顺序，1000+ 消息的流式场景须在后续实现中验证。

输入区支持多行与输入法。发送语义清晰：非输入法组合期间 Enter 发送，Shift+Enter 换行；处于组合输入时 Enter 只用于确认输入，不能误发送。发送按钮始终提供等价操作，并能看出当前是发送主持人消息、提交目标还是启动协作。

点名选择通过成员列表或 `@` 菜单完成，并显示“下一位：姓名”。主持人 `@Override` 请求进入下一位调度，不抢占当前正在生成的回合；普通模型文本中的 `@`、Pause、Stop 或类似指令都不具有主持人权限。持续指令有独立编辑与生效状态，不与一次性消息混为一谈。

修改或重新生成必须呈现版本关系与受影响分支。原文保持可追踪，不能无声覆盖共享历史。上下文摘要标注压缩范围，并允许查看该范围的历史原文；摘要不是删除原文的理由。

## 8. Run / Turn 状态与控制语义

状态、命令许可与回合结果以 [Main 状态机](../src/main/orchestrator/stateMachine.ts)、[RunService](../src/main/services/RunService.ts) 和 [共享类型](../src/shared/types/run.ts) 为准。Renderer 订阅 Main 快照与事件，不能用本地计时、文字匹配或按钮点击推导权威状态。

| Run 状态 | 推荐显示 | 控制呈现 |
| --- | --- | --- |
| `idle` | 待开始 | 提供开始；配置和目标可编辑 |
| `running` | 运行中 · 当前 Agent / 回合 | 提供暂停与停止；Step 和 Resume 不可用 |
| `pausing` | 正在暂停 · 当前回合结束后暂停 | 保持当前输出；可停止；重复暂停、Step 与 Resume 不可用 |
| `paused` | 已暂停 · 等待主持人操作 | 提供单步、继续与停止；保留下一步上下文 |
| `cancelling` | 正在停止 | 等待 Main 结果；禁用重复运行控制，保留消息阅读 |
| `cancelled` | 已停止 · 部分输出已保留 | 可查看历史；只有可用实现与 Main 条件满足时提供显式重试 |
| `completed` | 已完成 | 提供产物与历史入口；继续新任务需创建新的 Run |
| `error` | 运行失败 · 原因摘要 | 保留消息与错误详情；显式重试入口必须符合 Main 条件 |
| `interrupted` | 已中断 · 需要处理 | 先检查历史和部分输出；不自动恢复可能重复收费的请求 |

Pause 是软暂停：请求后继续完成当前回合，再停止后续调度；文案不能写“立即停止生成”。Stop 发出 Abort，请求终止当前生成及后续调度，保留部分文本；`cancelling` 与 `cancelled` 必须区分。Step 只在 `paused` 下可用，恰好执行一个下一回合；若仍有后续回合回到 `paused`，若这是最后一回合则进入 `completed`。Resume 从 `paused` 恢复后续自动调度，不能与 Step 合并成含糊的“播放”动作。

Turn 状态 `queued/pending/running/completed/failed/aborted/interrupted/cancelled` 与消息状态 `streaming/completed/failed/aborted` 分开处理。Run 已停止不等于此前所有消息失败；被 Abort 的消息显示“已中止 · 保留部分文本”，已完成的消息继续显示完成。无文本的失败消息也保留可辨认的失败位置和原因入口。

同步 Main 快照期间显示“正在同步运行状态”，避免重复开始或重复调用模型。命令发送期间可以显示请求待确认，但状态标签仍以 Main 为准；失败后反馈中文原因并保留当前阅读位置。未知状态以文字“未知状态”呈现并允许检查，不能默认当成完成。

预算、轮数与超时的限制必须显示来源和触发原因。自动限额触发暂停时说明原因，继续或调整限制需按 Main 实际能力提供；界面不得绕过硬性调度限制。

当前 M1 的重试、续写和中断恢复入口尚未完整实现；规范描述的是后续入口要求。不得将仅在类型或状态机中声明、服务实际仍拒绝的命令展示为可用功能，也不得用自动重试绕过缺失入口。

## 9. 产物与确认体验

PRD、会议纪要与行动项优先呈现结构化内容，附关联任务、Run 与来源消息。生成中、校验失败、草稿、可导出和已导出使用不同文字状态；“Run 已完成”不能替代产物结构校验或导出成功。

代码候选以文件列表、目标路径、内容和 diff 预览呈现。写盘前明确展示新增或覆盖的文件、路径校验结果与用户确认动作；错误路径阻止确认。只有用户人工确认且 Main 完成校验后才执行写入，写入后报告实际结果。模型生成代码不自动执行，预览与写盘不能被一个含糊的“应用”按钮混合。

大产物允许切换为专注预览，保留返回聊天入口。导出失败反馈具体可处理的原因；未完成或失败的结果不能使用成功色及“已保存”标签。

## 10. 可访问性与完整状态

后续实现必须验证以下要求：

- 正文与关键辅助文字相对实际背景至少 4.5:1；必要的控件边界、图标和焦点指示相对相邻颜色至少 3:1。色值表只是起点，应对亮暗主题、悬停、选中、错误等实际组合测量。
- 全部主要操作可用键盘完成；焦点清晰，顺序与阅读一致；菜单、抽屉和对话框有标题、关闭行为与正确焦点返回，不制造焦点陷阱。
- 按钮与图标具有可读名称，状态变化提供适度的辅助技术通知。流式 Token 不逐字高频播报，完成、暂停、停止和错误可简洁通知。
- 输入法组合期间不误发送、不吞字；中文长句、长模型名、路径与混合中英文不会裁切必要信息。
- 200% 缩放后主要内容重排，输入、状态与控制仍可达；不能要求用户恢复默认缩放才能操作。代码或 diff 可以在自身区域滚动。
- 遵循 `prefers-reduced-motion`。减少动画时取消平滑滚动与非必要过渡；状态含文字，不依赖旋转、闪烁或颜色变化。
- 空房间、首次配置、无 Key、同步、流式生成、错误、被停止、意外中断、预算限制与没有产物都有明确解释和可用下一步。

装饰性界面可以简化；必要说明不能以低对比、仅 Tooltip 或纯图标隐藏。所有状态先保证文字解释，再决定是否增加图标或颜色。

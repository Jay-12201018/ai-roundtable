### 继续讨论的 Main 端设计：为什么重新打开同一个 Run

- **历史**：成员要看到前面的全部内容。摘要（D107/D109）、消息版本与受影响标注（R12）、D095 引用格式都按 Run 组织；重新打开同一个 Run 就全部原样可用。新建关联 Run 要么复制历史（证据重复、版本关系断开），要么让上下文构建跨 Run 取数（改动 R05 的身份校验）。
- **事件 / cursor**：仍在同一个 Run 的序列上递增，Renderer 现有订阅不需要改；`host_updated` 与 `run_state_changed` 照常发出。
- **恢复**：异常退出后运行是 `interrupted`，在途的回答必须显式重试（`resume` 被拒），重试后才补完这一轮；不会自动重发（磁盘重启测试验证 0 次自动请求）。
- **预算账本 / 用量页**：每次回答仍按 D090 在发送前预留、结束后结算，记在同一个 Run 的账本上；用量页按运行汇总，自然包含继续的花费。
- **摘要覆盖范围**：编号沿用同一条时间线，已确认的摘要继续生效；继续的回合可以再被摘要覆盖。
- **时长**：继续时把当时的累计用时记下，时长上限从这一刻起重新给足；回合上限不变（继续的回合不计入）。
- **可继续的状态**：`completed`，或 `cancelled` / 非预算原因的 `error` 且全部回合已结算。停在半截的回合仍走重试 / 续写；因预算停下的运行本来就留在同一场讨论里（插话 + 追加并继续），不改。继续过的运行回应完就结束，不会回到原计划（停止后继续，也不会自动跑完剩下的计划）。

## 第 3 层：真实模型实测

**未验证**，由总控和用户一起做。建议脚本（DeepSeek `deepseek-flash`，用户自己的 Key，隔离试用 profile，预算 ¥1）：

1. 三位成员（起草 / 审查 / 综合），按顺序轮流 3 回合，勾选“每回合后暂停”。目标：设计校园跑腿平台试点方案。
2. 第 1、2 轮后暂停，输入 `@审查者 检查一下骑手收入那一段的数字`，确认“下一位：审查者（主持人点名，插入一轮…）· 之后回到原计划：综合者”，点「继续」。核对：审查者插入一轮，综合者照常综合；综合者的回答里用到了审查者的核对。（4 次请求）
3. 讨论结束后，输入 `@综合者 请总结最终方案`，确认输入框上方“只由综合者回应一次 · 预计最高约 ¥…”。核对：综合者在同一场讨论里回答、引用了前面的内容；侧栏仍只有这一场。（1 次请求）
4. 再输入（不带 @）`再各说一句：试点最大的风险是什么？`。核对：三位按顺序各回应一次，后面的成员不重复前面的观点。（3 次请求）
5. 全程核对：没有任何一次回答复述“写于前序修改之前”之类的规则文字；本场信息 › 进度显示“计划 3 / 3 回合 · 另有 5 轮插入（点名 1、继续讨论 4）”；用量页的请求次数与 DeepSeek 控制台一致。

预计花费：共 8 次请求。参照 2026-10-27 试用（6 次约 ¥0.052，高峰价），加上后面的请求上下文更长，按高峰价约 ¥0.08–0.12，空闲时段约一半。界面上的“预计最高”按每位写满单次上限（4096）和高峰价预留，会显示得高得多（一轮三位约 ¥0.27），结束后按实际用量结算。

## 遗留问题

- 继续时的“预计最高”是估算：每次发言按当时的上下文报价，再加上主持人这段话和此前回应按写满上限估出的输入。实际仍以每次发送前的预留为准，所以第一次发言是严格上界，后面几次是估算（中文按每 token 约 5 字节，取 6 字节）。
- 继续只能在讨论空闲时发起；运行中仍是插话 / 点名。
- 因预算停下的运行仍按原方式处理（插话 + 追加并继续）。追加后会先跑完原计划；如果主持人只想让某位成员回答，可以先点名。
- 本场信息 › 成员 / 进度、时间线标签仍按 R16 第一批的结构；R16 第二批如果改动输入框或侧栏，需要保留“继续讨论”与「新讨论」两个入口的区分。

### 继续讨论的 Main 端设计：为什么重新打开同一个 Run

- **历史**：成员要看到前面的全部内容。摘要（D107/D109）、消息版本与受影响标注（R12）、D095 引用格式都按 Run 组织；重新打开同一个 Run 就全部原样可用。新建关联 Run 要么复制历史（证据重复、版本关系断开），要么让上下文构建跨 Run 取数（改动 R05 的身份校验）。
- **事件 / cursor**：仍在同一个 Run 的序列上递增，Renderer 现有订阅不需要改；`host_updated` 与 `run_state_changed` 照常发出。
- **恢复**：异常退出后运行是 `interrupted`，在途的回答必须显式重试（`resume` 被拒），重试后才补完这一轮；不会自动重发（磁盘重启测试验证 0 次自动请求）。
- **预算账本 / 用量页**：每次回答仍按 D090 在发送前预留、结束后结算，记在同一个 Run 的账本上；用量页按运行汇总，自然包含继续的花费。
- **摘要覆盖范围**：编号沿用同一条时间线，已确认的摘要继续生效；继续的回合可以再被摘要覆盖。
- **时长**：继续时把当时的累计用时记下，时长上限从这一刻起重新给足；回合上限不变（继续的回合不计入）。
- **可继续的状态**：`completed`，或 `cancelled` / 非预算原因的 `error` 且全部回合已结算。停在半截的回合仍走重试 / 续写；因预算停下的运行本来就留在同一场讨论里（插话 + 追加并继续），不改。继续过的运行回应完就结束，不会回到原计划（停止后继续，也不会自动跑完剩下的计划）。

## 真实模型实测后的修改：@ 计划中的下一位不再多插一轮（2026-10-27）

现象（总控与用户 20:20 的 DeepSeek 实测，run fe274380）：A 发言后主持人发“@B 先核一下预算数字”，B 本来就是计划的下一位，实际顺序 A → B（插入）→ B（按计划）→ C，B 连说两次、多花一次请求。

改动：
- `interject.ts`：被 @ 的成员就是日程上的下一位（`scheduledNext`：运行中 / 暂停中、没有待执行的点名、下一位来自计划或正在进行的继续）时，不发 setOverride，只发插话；只写了 @ 没写话时什么也不发。提示“B 按计划就是下一位，会在发言时看到你这段话（没有多插一轮）”。
- `mention.ts`：@ 菜单里这位成员写“按计划就是下一位：只发插话，不多插一轮”；其他成员写“点名后插入下一回合发言”。
- 本场信息 › 成员：日程上的下一位不显示「点名」按钮（行上已有“下一位”标记），说明里加一句“按计划的下一位不用点名，直接在下方插话即可”。

## 遗留问题

- 继续时的“整轮最多”是估算：每次发言按当时的上下文报价，再加上主持人这段话和此前回应按写满上限估出的输入。实际仍以每次发送前的预留为准，所以第一次发言是严格上界，后面几次是估算（中文按每 token 约 5 字节，取 6 字节）。
- 继续只能在讨论空闲时发起；运行中仍是插话 / 点名。
- 因预算停下的运行仍按原方式处理（插话 + 追加并继续）。追加后会先跑完原计划；如果主持人只想让某位成员回答，可以先点名。

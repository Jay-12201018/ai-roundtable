实操中发现并直接修掉的问题：

1. 新讨论的输入框预填“设计一个校园跑腿平台”，在群聊里按回车就替用户说了一句话。群聊现在打开是空的，严格流程不变。
2. 每条短回复下面都有一行用量和按钮，再加上 30px 间距，聊天被拉得很散。群聊里这一行只在看这条消息（悬停或键盘焦点）时出现，位置保留，间距收到 6px。
3. “被打断”用的是整块提示框，比说的话还显眼。改成一行小字。
4. 最初的实现把前一条消息里被 @ 但还没轮到的人留到新一轮，和任务要求的“排队中的发言作废”不一致，在截图 10 里表现为小雨抢在阿哲前面回答旧问题。已去掉，严格按最新消息。
5. 输入法组合时菜单写“没有名字以 xiao 开头”。群聊里组合中保持完整列表。
6. 中文后面紧跟 `@`（“请@小雨”）原来打不开菜单，因为判断要求前面是空白。群聊里放开了，严格流程不变。
7. 停止对话框在群聊里没有意义（什么都不会丢），改成一键。

## 第 3 层实测后的修正（D154）

总控转来用户第一次真实模型实测（run dea6a6e7）的问题，这里没有读那个库，也没有调用真实模型，只用 fixture。**fixture 只能证明程序行为**：控制词、排几位、请求里有没有日期和规则，由测试保证；成员还编不编造、还跑不跑题，提示词有没有用，要等第 3 层再看。

| 问题 | 修正 | 怎么验证的 |
| --- | --- | --- |
| 编造事实、虚构承诺 | 群聊规则、默认人设、集合提示、long 的提示 | 断言每个群聊请求都有规则；单元断言默认人设没有职位 |
| 日期错 | Main 生成的应用指令 | 断言请求里有今天的日期和星期，重试时相同 |
| 打字“停止”没有停 | 控制词整句匹配 | 中止回复、中止调度、队列作废、不发请求、进历史；“停止吧”算，“停止这个方案，换一个”不算 |
| 简单问题两人都答 | 只排 1 位 | 多个种子下都是 1 位 |
| “1”排了 3 位 | 1–2 个字只排 1 位，不调度 | 1、好、嗯、ok、？都是 1 位且没有调度请求；“继续”仍走调度 |
| 换话题还接旧话题、总结太勤、单向输出 | 群聊规则和调度提示 | 只断言文字在提示里，效果要看第 3 层 |

四种现有方式：断言请求里没有日期和这些规则，前两条系统消息和原来逐字相同。

写测试时发现一个程序错误：单独的“好”被当成集合（全员回应），已修。

## 第二轮实测后的修正（D155）

同样只用 fixture 和真实的本机连接，没有读试用库，没有调用真实模型。

| 问题 | 修正 | 怎么验证的 |
| --- | --- | --- |
| 连接偶发失败要手动重试 | DNS、TCP、TLS 失败自动再试一次 | `tests/unit/providers/network.test.ts`：只重试一次、第二次能成功、写出后不重试、回复中断不重试、abort 不重试（包括等待期间）、guard 先查、应用拒绝的不重试。集成：服务只收到一个请求、用量正常、一次 `onDispatch` |
| 看不出死在哪一步 | 错误的 `phase` | 断言 `lastFailure` 和 `turn_failed` 里有阶段、没有地址；DNS 失败用量 `not_sent`，写出后 `unknown`；回复中断是 `response` |
| 一位失败卡住其他人 | 队列继续，就地重说 | 其他人照常说、回到等待；重说发同一份请求，位置不变，不调度；有人说话时拒绝；停止和严格流程仍然停下 |
| “大家”没有全员回应 | 全员规则 | 正反例都测了；集合和 @ 优先；顺序不固定 |
| 反复问、编造自己在做什么、重复答案 | 提示词三条 | 只断言文字在提示里，效果要看第 3 层 |

3 秒失败的原因没有查明，这次只是让它能自己恢复。如果真实环境里重试后仍失败，运行详情现在能看到是哪一步。

## 第 3 层：真实模型

前两次实测的结论见上。下一次要看，用用户自己的 Key。观察点：

- **是不是像群聊**：“集合开会！”是不是每人一句、不重样；简单问题是不是一两句；会不会回到报告腔、“首先其次”。
- **风格差异**：林舟、阿哲、小雨说话有没有区别，阿哲会不会真的挑刺，还是一味附和。
- **关思考后的耗时和 token**：DeepSeek、豆包、千问短回复的首字时间和 token，和没关时对比；Kimi、`glm-5.3` 系列、MiniMax Flash 关不掉，短回复要等多久。
- **调度 token 占比**：用量页“群聊调度”占总量多少；调度返回的 JSON 能不能解析（看 `group_chat_schedule_requests` 的 status），20 秒和 400 tokens 够不够。
- **只连了没有快模型的服务**（Kimi、智谱、混元、文心、MiniMax）时，只靠规则够不够用。这是 D152 的取舍。
- **任务类消息**：“写一份方案”时，是不是一位交付、一位简短回应，交付的质量有没有因为聊天口吻变差。第二期合并前还要和审查修订链对比深度。
- **连接失败**：运行详情里 `phase` 是什么；重试后是否恢复（请求数和 `not_sent` 的数量可以对照）。
- **打断**：被打断的半句话不进上下文（D151），新消息之后模型会不会接不上。
- **文档查实但没实测**：`fastReplyBody` 的参数只读了官方文档，真实请求是否都接受要在这一层看。

## 第三轮真实实测（2026-11-10，run b220cc27，提交 9ded430）

用户在隔离试用 profile 里用自己的 Key 跑，网络工具开着。结论取自试用数据库的记录，只读。

- 请求：8 次成员请求，7 次完成、1 次被主持人打断；0 次连接失败，没有触发重连。调度模型 0 次调用（四条消息都由规则分类）。
- `集合开会！`：三位各一句，3 秒内到齐（`gather`，短回复，关思考）。
- `这个方向大家怎么看：做一个校园二手平台`：三位都回应（`gather`，`medium`）。两位各等了 10.0 秒和 12.5 秒，见 D156。

- `停止`：阿哲的请求被中止，已输出的半句保留，状态 `aborted`；之后没有新的发言。
- 内容：没有编造事实，没有错日期，没有回到旧话题。问题：认领时问得多（三个问题），有一句“一天能给你看”，见 D156。
